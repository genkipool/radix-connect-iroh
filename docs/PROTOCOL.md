# Radix Connect over iroh — protocol v1

Radix Connect links the Radix Wallet (mobile) with the Radix Connector Extension
(browser). Today the link runs over a WebRTC data channel negotiated through the Radix
signaling server. This document specifies a second transport for the same link, built
on [iroh](https://iroh.computer): QUIC between two Ed25519-identified endpoints, with
connections established through an iroh relay server and upgraded to a direct path
when the network allows it.

The transport is a drop-in replacement for the data channel: it carries the very same
application messages (wallet interactions and responses, `linkClient`, `accountList`,
ledger requests and responses), so nothing above the transport changes.

## 1. Goals

- Same messages, same semantics as WebRTC (ordered delivery, a per-message receipt
  confirmation, immediate `notConnected` failures).
- No change to linking: the QR code, the stored links and the `linkClient` exchange are
  untouched, and links created before this transport existed work over it.
- Only the two holders of a link's connection password can reach each other; relays
  see neither the messages nor the password.
- No dependency on a discovery service: nothing about an endpoint is published.

## 2. Roles

| Role | Who | Behaviour |
|---|---|---|
| `connector` | Connector Extension | Listens. Accepts connections from the link's wallet only. |
| `wallet` | Radix Wallet | Dials the connector, re-dials with backoff while it should be connected. |

One session (one iroh endpoint) per link and per side.

## 3. Identities

A link is identified by its **connection password** `P`: 32 random bytes generated by
the Connector Extension, shown in the linking QR code and stored by both sides (the
same value the WebRTC transport uses for `connectionId = blake2b(P)` and for
encrypting signaling messages).

Each side's iroh endpoint key is derived from `P` with BLAKE3 in key-derivation mode:

```text
wallet_seed    = BLAKE3.derive_key("Radix Connect over iroh 2026-10-29 wallet endpoint key v1",    P)
connector_seed = BLAKE3.derive_key("Radix Connect over iroh 2026-10-29 connector endpoint key v1", P)
```

Each 32-byte seed is an Ed25519 secret key (RFC 8032 seed); its public key is the iroh
`EndpointId` of that end of the link. Both sides compute both ids, so each knows in
advance the single peer it may talk to.

Test vector — `P = cafe…cafe` (the two bytes `ca fe` repeated 16 times):

| Role | EndpointId (hex) |
|---|---|
| wallet | `4d99dc649e722e88092356956cb78d87dd24bae70b8110f492a4e843fe91f178` |
| connector | `efcc89cfbf2350783bcc70dd2908a034d765fa70abab6d00f62e236561d43aa8` |

## 4. Transport

- **QUIC with TLS 1.3 and raw public keys** (iroh). Both ends authenticate: the
  handshake proves possession of the secret key behind each `EndpointId`.
- **ALPN:** `radix-connect/iroh/1`. A new protocol version gets a new ALPN.
- **Relay:** both sides are configured with the same relay URL, like both sides of a
  WebRTC link use the same signaling server. The connector keeps a connection to that
  relay (its "home relay"); the wallet dials `EndpointAddr { id: connector_id, relay:
  relay_url }`. The relay forwards encrypted QUIC packets and helps the endpoints punch
  a direct UDP path when possible (never in a browser, which has no UDP).
- **No address lookup:** endpoints use iroh's `Minimal` preset; they publish no DNS or
  pkarr records.

Default relay: `https://euc1-1.relay.n0.iroh.link./` (n0's public relay, for
development). Production deployments are expected to run their own `iroh-relay`.

## 5. Admission

Both sides install a hook that runs inside iroh for every connection:

- before dialing: refuse any target other than the derived peer id or any ALPN other
  than `radix-connect/iroh/1`;
- after the handshake: close with application error `1` (`unauthorized`) any
  connection whose authenticated remote id is not the derived peer id.

The connector checks the remote id again before using a connection. The wallet's
endpoint registers no ALPN at all, so it refuses every incoming handshake.

A connector accepts at most 4 handshakes in parallel and gives each 15 s.

When an authenticated connection arrives while another one is active, the new one wins
and the old one is closed with application error `2` (`replaced`): the wallet only
dials again when it believes the previous connection is dead (app restart, network
change), and a dead QUIC connection can take a while to time out.

## 6. Messages

Every application message uses its own bidirectional stream:

```text
sender                                   receiver
  open_bi ───────────────────────────────▶ accept_bi
  write  <UTF-8 JSON message bytes>
  finish ───────────────────────────────▶ read to end (≤ max size)
                                           hand the message to the application
  read to end (≤ 1 byte) ◀──────────────── write <status byte>, finish
```

Status byte: `0x00` received, `0x01` rejected (too large or not valid UTF-8). A receiver
that refuses a message for its size also stops the stream with error code `1`.

- The message is exactly the JSON text the WebRTC transport sends after reassembly — no
  chunks, no hashes, no `packageType` envelope: QUIC already provides reliability,
  integrity, flow control and encryption.
- **Ordering:** a receiver reads one stream at a time, in the order the peer opened
  them, so messages are delivered in order (as over the ordered data channel).
- **Confirmation:** `send` completes when the status byte arrives, i.e. after the
  receiving side has queued the message for its application. This is the equivalent of
  WebRTC's `receiveMessageConfirmation`, on which the extension's request queues rely.
- **Limits (defaults):** 8 MiB per message, 10 s for the confirmation (as WebRTC), 60 s
  for an incoming message to arrive completely, 16 concurrently open streams per peer,
  no unidirectional streams.
- **Errors reported to the host:** `notConnected` (immediately, nothing sent),
  `timeout` (may have been delivered), `messageTooLarge` (nothing sent), `rejected`,
  `connectionLost`, `closed`.

Messages are delivered to the host through an event queue of 64 entries; while it is
full the session stops reading, so a host that cannot keep up makes the peer's sends
time out instead of growing memory.

## 7. Connection lifecycle

States: `connecting` (wallet dialing), `connected`, `disconnected`.

- The wallet dials, serves the connection until it ends, waits 0.5 s doubling up to
  15 s, and dials again. A dial attempt is abandoned after 20 s. `networkChanged()`
  (called by the host on connectivity changes) re-dials at once.
- The connector starts `disconnected` and becomes `connected` whenever an
  authenticated connection is accepted.
- Closing a session closes its connection with application error `0` and its endpoint.

## 8. Security considerations

**What protects the link.** Possession of `P`. An attacker without `P` cannot compute
either endpoint secret, so it cannot complete a handshake as the wallet (the connector
closes it) nor impersonate the connector (the wallet's handshake would fail). Knowing an
`EndpointId` does not help: BLAKE3 is preimage resistant, so the ids reveal nothing
about `P`. This is the same trust root as the WebRTC transport, where `P` authenticates
the signaling messages that pin the DTLS fingerprints.

**Confidentiality and integrity.** All application data is protected end to end by
QUIC/TLS 1.3 between the two endpoints; relays and network observers only see
encrypted packets. TLS 1.3's ephemeral key exchange gives forward secrecy: a later
leak of `P` does not decrypt recorded sessions.

**What relays learn.** The two endpoint ids of a link, when they are online, and the
timing and size of encrypted packets. Because ids are derived per link, a relay cannot
correlate the links of one wallet or one browser. No endpoint publishes anything to a
discovery service. A malicious relay can drop traffic (denial of service), like a
signaling or TURN server can today, but cannot read or forge it. Relay TLS certificates
are verified against the embedded web PKI roots.

**Domain separation.** The derivation contexts are unique to this protocol and role;
the derived keys are independent of every other use of `P` (blake2b connection id,
AES-GCM signaling encryption, the `L`-prefixed linking signatures) and of the
long-term Ed25519 keys of the wallet and the extension, which are not reused.

**Both sides can derive both keys.** As with any shared-secret scheme, either holder
of `P` could impersonate the other. That is inherent to links keyed by `P` and not a
new exposure: whoever holds `P` can already take over the WebRTC link.

**Resource limits.** Message size, concurrent streams, pending handshakes, read
timeouts and the bounded event queue cap what a peer — even an authenticated one — can
make the other side buffer.

**Implementation hygiene.** `P` and derived seeds are wiped from memory after use and
never logged; the core crate forbids `unsafe`; the only `unsafe` code is the one-time
Android JNI hand-over of the application context to iroh's DNS resolver.

## 9. Compatibility and coexistence with WebRTC

The transport is opt-in on both sides. Hosts may run WebRTC and iroh for the same link
at the same time; each message is sent on exactly one transport (iroh when connected,
otherwise WebRTC, falling back only when the first reports `notConnected`), and
messages are accepted from both. Peers that do not speak iroh simply never connect
over it.
