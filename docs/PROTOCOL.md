# Radix Connect over iroh — protocol v1

Radix Connect links the Radix Wallet (mobile) with the Radix Connector Extension
(browser). Today the link runs over a WebRTC data channel negotiated through the Radix
signaling server. This document specifies a second transport for the same link, built
on [iroh](https://iroh.computer): QUIC between two Ed25519-identified endpoints, with
connections established through an iroh relay server and upgraded to a direct path
when the network allows it.

The transport is a drop-in replacement for the data channel: it carries the very same
application messages (wallet interactions and responses, `linkClient`, `accountList`,
ledger requests and responses), so nothing above the transport changes.

## 1. Goals

- Same messages, same semantics as WebRTC (ordered delivery, a per-message receipt
  confirmation, immediate `notConnected` failures).
- No change to linking: the QR code, the stored links and the `linkClient` exchange are
  untouched, and links created before this transport existed work over it.
- Only the two holders of a link's connection password can reach each other; relays
  see neither the messages nor the password.
- Minimal publication: with the default public relays only the connector publishes
  which relay it uses (never an IP address); with a custom relay nothing is published.

## 2. Roles

| Role | Who | Behaviour |
|---|---|---|
| `connector` | Connector Extension | Listens. Accepts connections from the link's wallet only. |
| `wallet` | Radix Wallet | Dials the connector, re-dials with backoff while it should be connected. |

One session (one iroh endpoint) per link and per side.

## 3. Identities

A link is identified by its **connection password** `P`: 32 random bytes generated by
the Connector Extension, shown in the linking QR code and stored by both sides (the
same value the WebRTC transport uses for `connectionId = blake2b(P)` and for
encrypting signaling messages).

Each side's iroh endpoint key is derived from `P` with BLAKE3 in key-derivation mode:

```text
wallet_seed    = BLAKE3.derive_key("Radix Connect over iroh 2026-10-29 wallet endpoint key v1",    P)
connector_seed = BLAKE3.derive_key("Radix Connect over iroh 2026-10-29 connector endpoint key v1", P)
```

Each 32-byte seed is an Ed25519 secret key (RFC 8032 seed); its public key is the iroh
`EndpointId` of that end of the link. Both sides compute both ids, so each knows in
advance the single peer it may talk to.

Test vector — `P = cafe…cafe` (the two bytes `ca fe` repeated 16 times):

| Role | EndpointId (hex) |
|---|---|
| wallet | `4d99dc649e722e88092356956cb78d87dd24bae70b8110f492a4e843fe91f178` |
| connector | `efcc89cfbf2350783bcc70dd2908a034d765fa70abab6d00f62e236561d43aa8` |

## 4. Transport

- **QUIC with TLS 1.3 and raw public keys** (iroh). Both ends authenticate: the
  handshake proves possession of the secret key behind each `EndpointId`.
- **ALPN:** `radix-connect/iroh/1`. A new protocol version gets a new ALPN.
- **Relays.** A relay forwards encrypted QUIC packets between the two endpoints and
  helps them punch a direct UDP path when possible (never in a browser, which has no
  UDP). Both ends of a link make the same one of two choices:
  - **Public (default):** n0's public relays (North America east and west, Europe,
    Asia-Pacific). Each end connects to its closest relay and moves to another if it
    fails. The connector publishes which relay it uses — the relay URL only, never an
    IP address — as a signed pkarr record in n0's address lookup (`dns.iroh.link`);
    the wallet dials the connector's `EndpointId` alone and finds the relay through
    that lookup (pkarr over HTTPS, and DNS where available). Nothing to host or
    configure, which is what lets it run in production without a Radix-operated relay.
  - **Custom:** one relay URL configured on both ends (e.g. a self-hosted
    `iroh-relay`). The wallet dials `EndpointAddr { id: connector_id, relay: url }`;
    nothing is published anywhere.

## 5. Admission

Both sides install a hook that runs inside iroh for every connection:

- before dialing: refuse any target other than the derived peer id or any ALPN other
  than `radix-connect/iroh/1`;
- after the handshake: close with application error `1` (`unauthorized`) any
  connection whose authenticated remote id is not the derived peer id.

The connector checks the remote id again before using a connection.

Before any handshake work, the connector screens connection attempts:

- Through the relay the sender's endpoint id is attested (relay clients authenticate
  with their key): the link's wallet is always let in, attempts from any other id are
  ignored without an answer.
- Direct UDP attempts — which a browser never receives — must first prove they can
  receive at their source address (a stateless QUIC retry), then share a pool of at
  most 8 parallel handshakes of 15 s each, where any key can complete the TLS handshake
  and the hook then rejects it. Filling that pool never keeps the wallet out, since its
  attempts through the relay bypass it.

The wallet's endpoint registers no ALPN and drops every incoming attempt unanswered.

When an authenticated connection arrives while another one is active, the new one wins
and the old one is closed with application error `2` (`replaced`): the wallet only
dials again when it believes the previous connection is dead (app restart, network
change), and a dead QUIC connection can take a while to time out. A wallet whose
connection was replaced waits the longest back-off before dialing again, so two
sessions holding the same key (another device, a second app instance) do not keep
taking the link from each other.

## 6. Messages

Every application message uses its own bidirectional stream:

```text
sender                                   receiver
  open_bi ───────────────────────────────▶ accept_bi
  write  <length: u32 big-endian> <UTF-8 JSON message bytes>
  finish ───────────────────────────────▶ read the length, then exactly that many bytes
                                           queue it; wait until the application takes it
  read to end (≤ 1 byte) ◀──────────────── write <status byte>, finish
```

Status byte: `0x00` received, `0x01` rejected (too large, longer than announced, or not
valid UTF-8). A receiver that refuses a message for its size also stops the stream with
error code `1`. A stream that ends before the announced length, or is reset, is
discarded without an answer. A sender that abandons a message (cancelled, timed out)
resets its stream with error code `2` — never finishes it — so a partial message can
never pass for a complete one.

- The message is exactly the JSON text the WebRTC transport sends after reassembly — no
  chunks, no hashes, no `packageType` envelope: QUIC already provides reliability,
  integrity, flow control and encryption.
- **Ordering:** a receiver reads one stream at a time, in the order the peer opened
  them, so messages are delivered in order (as over the ordered data channel).
- **Confirmation:** `send` completes when the status byte arrives, which the receiver
  writes only once its application has taken the message from the session. A message is
  therefore never confirmed without having reached the application, even if the
  receiving session closes right after. It plays the role of WebRTC's
  `receiveMessageConfirmation`, on which the extension's request queues rely, but is
  stronger: WebRTC confirms once the chunks are reassembled, iroh once the application
  took the message. Hosts must therefore keep reading events while they send — a host
  that waits for its own send before reading would leave the peer's messages
  unconfirmed. If the
  sender stops waiting first (timeout), it stops the stream and the receiver withdraws
  the message, so a retry does not deliver it twice; the remaining window — the
  application took the message but the status byte was lost with the connection — is
  inherent to any acknowledgement and reported as `timeout`/`connectionLost`, which mean
  "may have been delivered".
- **Timeouts:** getting a message across (open, write, the peer acknowledging every
  byte) and getting it confirmed are bounded separately, so a large message on a slow
  link is not cut short by the confirmation timeout.
- **Limits (defaults):** 8 MiB per message; 60 s for a message to get across, in both
  directions; 10 s for the confirmation once it arrived (as WebRTC); 16 concurrently
  open streams per peer; no unidirectional streams.
- **Errors reported to the host:** `notConnected` (immediately, nothing sent),
  `messageTooLarge` (nothing sent), `rejected` (refused by the peer, not delivered),
  `timeout` and `connectionLost` (may have been delivered), `closed`.

The receiver reads the next message only after the application took the previous one,
so a host that cannot keep up makes the peer's sends time out instead of growing memory.

## 7. Connection lifecycle

States: `connecting` (wallet dialing), `connected`, `disconnected`.

- The wallet dials, serves the connection until it ends, waits 0.5 s doubling up to
  15 s, and dials again. A dial attempt is abandoned after 20 s. `networkChanged()`
  (called by the host on connectivity changes) re-dials at once.
- The connector starts `disconnected` and becomes `connected` whenever an
  authenticated connection is accepted.
- Closing a session closes its connection with application error `0` and its endpoint.

## 8. Security considerations

**What protects the link.** Possession of `P`. An attacker without `P` cannot compute
either endpoint secret, so it cannot complete a handshake as the wallet (the connector
closes it) nor impersonate the connector (the wallet's handshake would fail). Knowing an
`EndpointId` does not help: BLAKE3 is preimage resistant, so the ids reveal nothing
about `P`. This is the same trust root as the WebRTC transport, where `P` authenticates
the signaling messages that pin the DTLS fingerprints.

**Confidentiality and integrity.** All application data is protected end to end by
QUIC/TLS 1.3 between the two endpoints; relays and network observers only see
encrypted packets. TLS 1.3's ephemeral key exchange gives forward secrecy: a later
leak of `P` does not decrypt recorded sessions.

**What relays and the address lookup learn.** A relay learns the two endpoint ids of a
link, their IP addresses, when they are online, and the timing and size of encrypted
packets. With the public relays, n0's address lookup also stores, per connector
endpoint id, which relay it uses (a signed record that contains no IP address and
nothing about the user). Because ids are derived per link, the ids themselves do not
link the links of one wallet or one browser; whoever operates a relay or the lookup can
still correlate them by IP address and timing, as a signaling or TURN server can today.
With a custom relay nothing is published. A malicious relay — or a tampered lookup record, which the
connector's signature prevents — can drop traffic (denial of service), like a signaling
or TURN server can today, but cannot read or forge it: the QUIC handshake still
authenticates the derived endpoint keys. Relay TLS certificates
are verified against the embedded web PKI roots.

**Domain separation.** The derivation contexts are unique to this protocol and role;
the derived keys are independent of every other use of `P` (blake2b connection id,
AES-GCM signaling encryption, the `L`-prefixed linking signatures) and of the
long-term Ed25519 keys of the wallet and the extension, which are not reused.

**Both sides can derive both keys.** As with any shared-secret scheme, either holder
of `P` could impersonate the other. That is inherent to links keyed by `P` and not a
new exposure: whoever holds `P` can already take over the WebRTC link.

**Resource limits.** Message size, concurrent streams, pending handshakes, read
timeouts and the bounded event queue cap what a peer — even an authenticated one — can
make the other side buffer.

**Plain-HTTP relays.** Relays are reached over HTTPS; plain HTTP is accepted only for
loopback, private and link-local addresses (development relays). Messages stay end-to-end
encrypted either way, but over plain HTTP an on-path observer would also see the
endpoint ids.

**Implementation hygiene.** `P` and the derived seeds are never logged. The copies
the library owns (the parsed password, the derived seed, the byte buffers handed over by
the bindings) are wiped with `zeroize`; copies outside its control are not (the host's
own `ByteArray`/`Uint8Array`, uniffi's transfer buffer, values moved through async state
machines), which is why hosts keep `P` in their usual secure storage and pass it only
when starting a session. The core crate forbids `unsafe`; the only `unsafe` code is the
one-time Android JNI hand-over of the application context to iroh's DNS resolver.

## 9. Compatibility and coexistence with WebRTC

The transport is opt-in on both sides. Hosts may run WebRTC and iroh for the same link
at the same time; each message is sent on exactly one transport (iroh when connected,
otherwise WebRTC, falling back only when the first reports `notConnected`), and
messages are accepted from both. Peers that do not speak iroh simply never connect
over it.
